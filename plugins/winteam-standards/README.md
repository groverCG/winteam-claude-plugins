# winteam-standards

General-purpose code standards for the WinTeam mobile app. **Not branch-specific** — unlike its sibling
`timeclock-refactor`, everything here is true on `master` and on any feature branch.

## What's in here

|---|---|---|

| `skills/keeping-core-methods-small` | automatic | 10-line method bodies (flag at 15) and max 3 parameters, **Core only** |
| `skills/naming-and-documenting-members` | automatic | `///` docs on every method; `//` comments only for formulas; naming rules |

Skills and commands are addressed with the plugin prefix — `/winteam-standards:code-style`. The bare forms do
not resolve. Inside this plugin, prose cross-references between skills stay bare
(`see \`response-entity-sibling\``) because they are labels, not invocations; **the prefix is for commands**,
which must be addressed explicitly. **Anything outside this plugin — the agents in `.claude/agents/` especially
— must use the prefixed form.**

## Why the skills are automatic and the commands are not

The seventeen skills above carry no `disable-model-invocation`, so their descriptions load into context and Claude
invokes them when they apply. That is the point: a size cap, a teardown rule, or a Manager's return type is only
useful if it fires *before* the code is written, and you will not remember to ask.

The five commands are manual because none of them is a guardrail. Four are **sweeps** — you want a ranked
backlog when you have decided to spend time on it, not while you are trying to ship something else — and
`new-slice` additionally because it writes files (see below).

**That line is what settled `mvvm-audit`.** It was a manual-only skill (`auditing-mvvm-boilerplate`) until it was
converted, and the conversion is worth understanding as a rule rather than a one-off: **a skill that can only be
invoked by hand is a command wearing a skill's clothes.** Making it a command bought two things a skill cannot
have — `argument-hint` for scoping, and `allowed-tools` to *enforce* its "report first, migrate only what the
user picks" rule instead of leaving it to prose. The test to apply next time is not "manual or automatic" but
**"does it report, or does it change code?"** Reports are commands; rules that must land before the code exists
are skills.

Expect the two size skills to fire on most C# edits, and `shaping-manager-contracts` on every Manager edit.
That is inherent to a 10-line method cap and a 13-file boundary violation; it is the trade being made
deliberately. `building-vertical-slices` is scoped to *"has no files yet"* precisely so it does **not** join
them — if it starts firing on ordinary edits, narrow its description rather than making it manual.

## The hooks, and why there are ten

A skill's `description` only competes for attention at turn start. By the time a Manager is actually being
written the model is mid-execution, and two cases were observed where nothing fired at all: **executing an
already-approved plan** that already named the file and method shapes, and **writing a file through something
other than `Write`**. The hooks are the deterministic half of the answer; the shared `when_to_use` block on
every skill (convention 9) is the model-facing half.

| Hook | Event | Covers |
|---|---|---|
| `entity_pair_brief.py` | `PreToolUse`, `Edit`/`Write` | Path match only. Emits the pair rules *before* the file is authored |
| `presentation_brief.py` | `PreToolUse`, `Edit`/`Write` | Path match only. Six briefs — xib/storyboard, layout, drawable, values, asset catalogue, `AppStrings` |
| `check_cs_edit.py` | `PostToolUse`, `Edit`/`Write` | Parses the result: size, parameters, teardown, entity pairs |
| `check_comments.py` | `PostToolUse`, `Edit`/`Write` | Parses the result: missing and incomplete `///`, narrating `//`, commented-out code |
| `check_presentation_edit.py` | `PostToolUse`, `Edit`/`Write` | Parses the result: hardcoded colours and dimensions, double-faded drawables, static styling in setup methods, `AppStrings` drift |
| `check_member_order.py` | `PostToolUse`, `Edit`/`Write` | Parses the result: state declared below behaviour, a single-caller helper above its caller. All three projects, and never reaches the `Stop` hook |
| `sweep_tool_writes.py` | `PostToolBatch`, no matcher | Everything else — a Bash heredoc, `sed -i`, `tee`, `cp`, an MCP server's own file-creation call |
| `plan_budget_brief.py` | `PreToolUse`, no matcher | Gated on `permission_mode == "plan"`. The budget card, once per planning round |
| `plan_handoff_brief.py` | `PreToolUse`, `ExitPlanMode` | Reads the plan, names its unbudgeted files, routes the other axes on its text |
| `enforce_session_standards.py` | `Stop`, no matcher | Everything the session touched, re-checked at end of turn. The only hook that blocks |

**The presentation pair closed a gap that was structural rather than a wording problem.**
The four presentation skills — `declarative-static-styling`, `checking-dark-mode`, `sizing-for-tablets`,
`appstrings` — are the only cluster here whose trigger material is *not* `.cs`, and all three of the original
hooks return early on anything that is not a `.cs` file. The entire markup surface therefore had no
deterministic coverage at all: a hundred-odd xibs and storyboards, as many layout XMLs, the drawables, the
asset catalogue and `AppStrings.resx`. The sweep now watches those extensions too, confined to the two
platform projects and Core's `Resources/` folder because `.xml` and `.resx` are far too common to accept
repo-wide.

**Every check in `check_presentation_edit.py` was counted against the whole repo before it shipped, and five
candidates were dropped because the count came back wrong.** A hex literal in a *drawable* turns out to be
the house style in the majority of them, while the same literal in a *layout* is vanishingly rare; a font
with no tablet `<variation>` is the majority case, as is a `@dimen` with no `values-large` override and an
imageset with no dark asset. All five are still stated in `presentation_brief.py`, where a rule costs
nothing, and all five are swept by `/winteam-standards:ui-audit`, where the user has opted in. The module
docstring records each one with its number so nobody adds them back — **that list is the most useful thing
in the file.** The lesson generalises: three of the five looked obviously right until they were counted.

**Why the third one watches the filesystem instead of matching tool names.** A list of tools that can write a
file is wrong the moment someone installs a new MCP server. The sweep instead asks git what changed and
compares mtimes against a per-session stamp, so it covers writers that do not exist yet. It excludes paths the
same batch wrote through `Edit`/`Write`, because `check_cs_edit.py` already reported those and one advisory
printed twice reads as a bug.

**The stamp is what keeps it quiet.** Without it, every batch would re-report every dirty file for the rest of
the session. `SessionStart` lays the mark down so the first batch already has a floor to measure against. A
batch made up entirely of known read-only tools returns *without* advancing it — a backgrounded shell can land
a file during that window, and moving the floor past it would lose it for good. An unknown tool name is not on
the read-only list and therefore still triggers a sweep; that polarity is the whole point.

**The last pair moved the whole thing one step earlier, into the plan.** The two hooks above that fire
before a write still fire *as the file is authored* — which is late, because by then the plan has already
named the file, the class and the method shapes. That is the first of the two silent-failure cases this
section opens with, and it was only ever half-addressed: the shared `when_to_use` block tells the model an
approved plan is not an exemption, but nothing put the numbers in front of it while the plan was being
written. Over the saved plans on this machine, **most name `WinTeam.Mobile.Core` and only a quarter of those
state any size budget at all** — the rest hand execution a shape nobody costed, and the cost surfaces as a
`check_cs_edit.py` advisory and a split afterwards, which is the expensive path `keeping-files-small` exists
to prevent.

`plan_budget_brief.py` therefore carries **no matcher** and gates on `permission_mode == "plan"` instead. The
first tool call of a planning round is whatever gets reached for first — a `Read`, a `Grep`, an `Agent`
launch — and enumerating those names is the same mistake the sweep avoids for writers. The trade is that at
that moment the plan does not exist yet, so there is nothing to route on and the card is the *universal*
half: caps, the parameter limit, the `///` rule, the layer order. **The plan file's own `Write` was
considered as the trigger and rejected**, even though it could be routed: it lands after the plan content is
composed, and roughly half of the measured sessions write the plan file exactly once, so a brief there would
influence nothing in those.

`plan_handoff_brief.py` picks up the routed half on `ExitPlanMode`, where `tool_input.plan` hands it the
finished text. **It adds no coverage and that is not why it exists** — no measured session reaches
`ExitPlanMode` without having written the plan file first. It exists for *when* its context lands: still in
the window as the approved plan starts being executed, which is exactly the moment named at the top of this
section. It is a hand-off note into execution, not a late attempt to fix the plan. It also clears the budget
card's per-round stamp, which is the only reason these two are a pair rather than two independent additions.

**It is the one brief here that is not one-per-write, and its routes had to be counted twice.** The
one-brief rule exists because a xib and a drawable have nothing in common; a single plan legitimately spans
a Manager and two xibs, so suppressing an axis would silently drop it. The first cut then routed on prose —
the words "label", "alert", "placeholder" for `appstrings`, a bare `*Manager` mention for the entity axis —
and fired on nine plans in ten, which is wallpaper. Re-anchoring every route on a path or a real code token
(`WinTeam.Mobile.Core/Entities/`, `AppStrings`, `Bootstrap.cs`, `[Inject]`, the actual subscription calls)
brought it down by a third. **Plans always spell the full project prefix**, which is what makes path
anchoring viable and is worth knowing before anyone loosens it.

**Eight of the nine share one contract: advisory only, exit 0, never block.** A `PreToolUse` hook *can*
return a `permissionDecision` and refuse the write, which is the only genuinely deterministic lever available
during a write — a hook cannot invoke a skill, so injected context is otherwise the ceiling. It is deliberately
not used: a false positive would stall an edit, and the never-block invariant is worth more than the extra
determinism.

`plan_handoff_brief.py` could deny an `ExitPlanMode` too — the CLI hands the reason back and asks for a
revised plan, so it would not even halt the turn — and it declines for the same invariant plus one reason
specific to it: **a plan check can only grep prose.** It can see that a plan names a file with no number
beside it; it cannot see whether a stated number is honest. Blocking on that grades the phrasing, and the
cheapest way to satisfy it is boilerplate budget lines that change no code. `check_cs_edit.py` counts real
lines in a real file. **Enforce where you can measure; inform where you cannot.**

### `enforce_session_standards.py` is the ninth, and it blocks

That last sentence is also what licenses the exception. **Everything the `Stop` hook reports is a counted line
in a real file**, which is the same side of the dividing line `check_cs_edit.py` sits on and the opposite side
from a plan's prose. It was added because the eight advisory hooks share a blind spot that no wording fixes:
they all fire *mid-write*, their advisories are suggestions, and the mtime stamp that keeps the sweep quiet
also guarantees an ignored advisory is **never raised a second time**. Nothing verified that a session ended
with its own files clean, and the cheapest way to satisfy an advisory was to keep going.

It fires once per turn, takes the files whose mtime is past a session-start mark, runs all four checkers over
them, and returns `{"decision": "block", "reason": ...}` when something is wrong. Its own floor rather than the
sweep's: that one advances on every tool batch, and this hook needs a mark that does not move or "changed this
session" decays into "changed since the last batch".

**What makes blocking safe is that every finding is still HEAD-relative.** 294 Core methods are over the length
cap and 929 documentation findings exist already; a hook that blocked on those would be unsatisfiable, and an
unsatisfiable hook gets deleted rather than obeyed. The checkers only fire when an edit made a file worse, so
the block is always about the author's own work.

Three guards bound it, and the third is the one worth defending:

1. `stop_hook_active` — already a continuation this hook caused, so report and stop.
2. A cap on findings in the reason. That text is the next turn's instructions, not a report.
3. **A per-session ledger: a file that has blocked once is never blocked again.** Some findings are a judgment
   call rather than a fix — an over-cap file needs a responsibility taken out, which needs the feature's
   context, and sometimes the honest answer is "not here, not now". A hook with no escape from that is a hook
   that gets disabled, so it grants one. The reason text says as much, and separates the mechanical findings
   from the judgment ones for exactly this reason.

The relent path reports through `systemMessage`, not `additionalContext`. A `Stop` hook that does not block has
no channel to the model — the turn is over — so the outstanding findings go to the **user**, who is the one who
can decide they are acceptable.

### The comment checks, and the number that shaped them

`check_comments.py` closed the last gap between the skills and the hooks: `naming-and-documenting-members`
requires a `///` block on every method and forbids a `//` that narrates a body, and until it existed **neither
rule was measured anywhere.** Both were counted against the whole repo first, per the rule above.

**912 of 948 public and protected members in Core carry no `///` block — 96%.** The house style is currently
the inverse of the rule, which decided the gate: the check fires when the *declaration line itself* changed —
a new member, or an edited signature — and deliberately not when a line deep inside an existing undocumented
method changed. The wider gate the length check uses (any line in `decl..end`) would have turned every edit to
an existing method into a documentation advisory. That is not a stricter hook, it is a muted one.

The comment rule measured far smaller: **226 narrating comments and 25 commented-out-code lines**, reported as
two findings because they have two different fixes. **A first pass put those at 426 and 157**, using an `awk`
proxy that read brace depth `>= 2` as "inside a method" — which over-counts by 258, because a file-scoped
namespace puts class-level members at depth 2, as do property accessors and object initializers. Worth knowing
before anyone re-measures with a grep and concludes the check is missing things: the grep is wrong, not the
check.

`check_cs_edit.py` owns the architecture checks, `check_presentation_edit.py` owns the presentation ones,
`check_comments.py` owns the documentation ones, and the last two import the first's git helpers and method
parser. `sweep_tool_writes.py` and `enforce_session_standards.py` import all three. There is deliberately no
second copy of the parser — it would drift, and the thresholds it enforces are the reason any of this exists.

**`code-style` imports them too, and that was the last piece of drift to go.** The command used to re-derive
the caps in `awk` and write a throwaway parser to the scratchpad, which cost a permission prompt on every run
and disagreed with the hook about how to count a file's last line. It now runs `scan_standards.py`, which calls
the same `advisories_for()` the hooks call — with one difference, named explicitly in that function: hooks pass
`report_all=False` and see only what an edit made worse, the command passes `report_all=True` and sees the
backlog. **One parser, two gates.** Without the flag a repo-wide scan of a clean tree would report nothing,
which is how a report ends up agreeing with a hook by saying nothing at all.

## `new-slice` writes files, and that is a deliberate exception

`code-style`, `leak-audit` and `mvvm-audit` are read-only because they are **audits** — not because read-only is
a plugin principle. A scaffolder that cannot write is just a skill printed twice, so `new-slice` carries `Write`
and `Edit`.

What is *not* negotiable is `disable-model-invocation: true`. An eight-file scaffold that appends to
`Bootstrap.cs`, `NavigationRoutes.cs`, `AppCoordinator.Navigation.cs` and a parent fragment must never fire on
inference. Its `## Rules` section carries the rest of the safety contract: refuse if a target exists, append-only
edits, a diff preview before writing, `TODO` markers instead of guessed REST routes, and no staging or
committing.

## The agents are not in here — they live in `.claude/agents/`

`senior-reviewer`, `memory-leak-hunter`, `ticket-analyst` and `ux-reviewer` sit in **`.claude/agents/`** at
project level. They are committed, so they work for everyone who clones with no install step. They are now the
only Claude Code assets outside this plugin — `.claude/skills/` no longer exists.

That is deliberate, and it is the opposite of the choice made for the skills below. The reason: **an agent is
not supposed to change your code.** All four are report-only, none has `Write` or `Edit` in its `tools`, and
each body says so explicitly, so the worst a teammate who never asked for one can realistically get is an
unrequested opinion. The opt-in barrier that protects them from an unwanted hook or an auto-firing skill is
buying much less here — it would mainly make the reviewers undiscoverable to anyone who skipped the install.

**Be precise about how strong that is.** All four hold `Bash`, because they need `git diff` and `git show`, and
`Bash` can write via `sed -i` or a redirect. `tools:` takes bare tool names only — `Bash(git diff:*)` is not
valid there and grants nothing rather than narrowing — so the read-only property rests on the missing
`Write`/`Edit` grant plus an instruction, not on a sandbox. Closing that gap means a `PreToolUse` hook on
`Bash` per agent. Worth doing if these ever run unattended.

**State the cost honestly, because it is not zero.** Claude delegates to an agent whenever a task matches its
`description`, without being asked — that is the normal mechanism, so these *do* fire on their own. Their
descriptions also occupy context so Claude knows they exist. Committing them means every teammate gets four
reviewers that may speak up uninvited. That is judged an acceptable trade **only** because they do not write;
if one ever gains `Write` or `Edit`, this argument collapses and it belongs behind an install like everything
else.

Three of them read this plugin's skills when it is installed: `senior-reviewer` uses ten,
`ux-reviewer` uses five, and `memory-leak-hunter` uses `tearing-down-subscriptions`.
All three are written to **state plainly when a skill did not resolve** rather than quietly producing a thinner
review, so an uninstalled plugin degrades visibly instead of silently. `ticket-analyst` depends on none.

`ux-reviewer` is the one whose exposure changed: its five skills are exactly the set that used to live in
`.claude/skills/`, where they were
unconditionally present. They now ship here, so declining the install leaves it with no theming, sizing or
string checks at all — which is exactly why it gained the same unresolved-skill fallback `senior-reviewer` has.

`timeclock-refactor` keeps its own `refactor-parity-auditor` inside the plugin, because that one references a
specific commit and types that exist only on the refactor branch, and should be retired or promoted together
with the rest of that plugin.

## Why this is a plugin and not plain project skills

Three reasons, and the first is the load-bearing one:

- **Opt-in.** `.claude/skills/` loads for everyone who clones. A plugin has to be installed first, so a hook and
  a set of opinionated caps cannot appear in a teammate's session just because they pulled. Nothing here is
  enabled by default — see *Installing it*.
- **It ships a hook, commands and skills as one unit.** A hook can go straight into `.claude/settings.json`
  with no plugin at all — so the plugin is not buying capability, it is buying cohesion: one directory, one
  thing to install, review or retire.
- **The caps are opinionated enough to want a name on them.** A 10-line method limit is a team decision, and a
  plugin makes it a named artifact rather than loose files.

**The consolidation finished the job.** Five skills — `appstrings`, the theming pair, `declarative-static-styling`
and `response-entity-sibling` — predated this plugin and lived in `.claude/skills/`. That split made the
cohesion argument above false in practice: `building-vertical-slices`, `shaping-manager-contracts`,
`reusing-existing-helpers` and `new-slice` all cited skills this plugin did not own and could not ship. A
teammate who never installed this plugin got a `new-slice` command that deferred `AppStrings` work to a skill it
could no longer name. They now ship here, and `.claude/skills/` is gone.

The cost is honest and worth stating: those five used to load unconditionally on clone, and now require an
install like everything else. That is the same trade already made for the other eleven — but it is a real
reduction in guaranteed availability, and worth knowing if someone reports a missing theming or `AppStrings`
check.

## Installing it

**This plugin is optional and nothing installs it for you.** The committed `.claude/settings.json` registers the
`winteam-local` marketplace only, so `/plugin` lists this plugin but leaves it disabled until you opt in.

Two commands, once per machine:

```bash
claude plugin marketplace add ./.claude/plugins        # only if /plugin does not already list it
claude plugin install winteam-standards@winteam-local -s local
```

**`-s local` matters.** The default scope is `user`, which would enable these caps in *every* project on your
machine. `local` records the choice in the gitignored `.claude/settings.local.json`, so it stays per machine and
never lands in a commit. Uninstall with the same flag:

```bash
claude plugin uninstall winteam-standards@winteam-local -s local
```

> Two similarly-named directories, easy to mix up: **`.claude/plugins/`** (this repo, hand-written source, the
> marketplace root) versus **`~/.claude/plugins/`** (your home directory, generated by the CLI, holds the
> install cache and marketplace registry). Never edit the latter by hand.

## Working on this plugin

**Edit the files here, then bump `version` in `.claude-plugin/plugin.json`.** The bump is not optional: an
installed copy is served from a version-keyed cache under `~/.claude/plugins/cache/`, so without it a teammate
keeps the old rules and `marketplace update` reports success while changing nothing. Bump the **minor** version
for a new or removed skill/command, the **patch** for wording inside one.

**If a change doesn't apply, suspect a pinned install before you suspect the edit.** Check your entry in
`~/.claude/plugins/installed_plugins.json` — a `version` behind the manifest means you are on a stale cache:

```bash
claude plugin marketplace update winteam-local
claude plugin update winteam-standards@winteam-local -s local
# still stale? force it:
claude plugin uninstall winteam-standards@winteam-local -s local
claude plugin install   winteam-standards@winteam-local -s local
```

Iterate against this directory directly, with no cache in the way:

```bash
claude --plugin-dir .claude/plugins/winteam-standards
```

Validate after changes:

```bash
claude plugin validate .claude/plugins
claude plugin validate .claude/plugins/winteam-standards --strict
```

`thresholds.json` in this directory is the source of truth for the size caps — the hook reads it, the
`code-style` command applies it, and the two size skills cite it. Change a cap there, not in four places.

## Contributing

Anyone on the team can change these standards. The loop is **edit → bump `version` → validate → push**, and the
bump is the step that gets forgotten.

What is specific to this plugin — where things go:

| Change | Location |
|---|---|
| A rule Claude should apply while writing code | `skills/<gerund-name>/SKILL.md` |
| An on-request sweep or audit you invoke by name | `commands/*.md`, with `disable-model-invocation: true` |
| A deterministic check on every edit | `hooks/check_cs_edit.py` — advisory only, must never block |
| A deterministic check on markup, or a presentation rule | `hooks/check_presentation_edit.py` — same contract, and **count the candidate repo-wide before adding it** |
| A check that must survive a non-`Write` writer | `hooks/sweep_tool_writes.py` — same contract; import the checks from `check_cs_edit.py`, never copy them |
| A rule that must land *before the plan is written* | `hooks/plan_budget_brief.py` for the universal card, `hooks/plan_handoff_brief.py` for anything routed on the plan's text — and **count the route against `~/.claude/plans/` before adding it** |
| A reviewer or analyst persona | `.claude/agents/` — **outside this plugin**, for the reason argued above |

Four things that are easy to get wrong:

- **Read the conventions below before adding a skill.** They are the bar, especially the ≤200-character
  `description` and the ~100-line target. A skill that fires on everything is worse than no skill.
- **Get the reference form right.** Inside this plugin, prose cross-references between auto-firing skills stay
  **bare** (``see `response-entity-sibling` ``). Commands take the `/winteam-standards:` prefix because they
  must be addressed explicitly, and **anything outside this plugin — the agents especially — must use the
  prefixed form** or it will not resolve.
- **Never tell the model to run a command.** Nothing invokes a slash command on the model's behalf, so
  ``run `/winteam-standards:code-style` `` inside a skill is a dead end. Write ``ask for `/…` `` instead.
- **Don't forget the `version` bump, and never move it backwards.** Nothing enforces it yet, so it is a review
  item — and a reset to a number someone already installed is the same bug as no bump at all.

## Conventions for adding a skill here

1. **Name it verb-first, gerund for a process** — `keeping-files-small`, not `file-size-rules`. Letters,
   numbers and hyphens only.
2. **Keep `description` to ≤ 200 characters — a hard limit, see 7 — and state only *when to use it*.** Never summarise the skill's
   workflow there. A description that describes the process becomes a shortcut agents take instead of reading
   the body, and the body stops being read at all.
3. **Prefer a generic code snippet over a repo file reference** for anything teaching a pattern. Where a
   specific location is genuinely the deliverable, put it in a `## Known offenders` section at the end.
4. Follow the section skeleton the existing skills use: title → why it matters and what it costs to get wrong
   → `## When to use` → `## When NOT to use` → rules or a decision table → `## Verify` with the literal build
   command. Aim for ~100 lines; treat 140 as the ceiling. Two skills are over it and both carry a second
   artifact the rules alone do not: `reusing-existing-helpers` at ~160, for a search procedure *and* a
   placement table, and `shaping-manager-contracts` at 141, for the file-by-file offender list the repo's
   most-violated boundary needs. **Those are the exceptions, not a new budget** — and note the test is what
   the extra lines *are*, not how close to 140 you land. A third skill does not get to be 141 for prose.
   The middle section has two shapes: guardrail skills use `## Rules`, and the procedural ones — `appstrings`,
   `response-entity-sibling`, `declarative-static-styling` — use numbered `## Steps` or
   `## Part N` instead, because they describe a task with an order rather than constraints to satisfy. Either
   is fine; everything around it stays the same.
5. **State what the build cannot catch.** Most rules here fail at runtime, not compile time; a `## Verify`
   section that stops at `dotnet build` is misleading.
6. **If almost no existing code follows the rule, say so above `## When to use`, not only in
   `## Known offenders`.** A trailing offenders list works when the rule already has majority support: most
   files conform, so the stragglers read as stragglers. It fails at *zero* conformance — an agent reads the
   rule, opens the nearest real file, and pattern-matches on the violation. `writing-use-cases` is the case in
   point, with **zero** of the existing use cases conforming, and states the mismatch up front in a blockquote.
   The conformance ratios themselves belong to each skill's `## Known offenders`; see 8.
7. **Every `description` must be ≤ 200 characters.** Not "about 200" — the convention is only useful if it is
   checkable, and an over-long description still loads and still works, so nothing else will catch it.
8. **No exact repo figures in this README.** A count belongs to the skill or command that owns it. Here, use
   the rounded form — "double-digit", "several hundred", "zero conformance" — or name the owning skill and let
   a reader go there. Three exact figures once accumulated here, in the file that defines the conventions, one
   of them wrong and the other two waiting to be. This README is edited far less often than the code it would
   describe, so a number here goes stale silently and nothing surfaces it.

9. **Every skill carries the shared `when_to_use` block, verbatim.** It names the two cases where skills were
   observed silently not firing — mid-execution of an already-approved plan, and a file written by something
   other than `Write`/`Edit`. `when_to_use` is appended to `description` for trigger matching against a
   *combined* 1,536-character budget, which is why the invariant lives there instead of being pasted into
   seventeen descriptions and blowing convention 7. Copy it from any existing skill and do not reword it per
   skill: the point is that it reads as one rule, not seventeen suggestions.
