# Keep a file down to one responsibility

A file that grows past its cap has almost always taken on a second responsibility. The cap is a symptom
detector, not the problem — the problem is that nobody can hold the file in their head, and every change to
it risks something unrelated.

**This fires while you write, not afterwards.** By the time a file is 600 lines the cheap seams are gone and
splitting it is a week of work. At 250 the seam is usually obvious and takes twenty minutes.

## Caps

| Location | Cap | Flag at |
|---|---|---|
| Anything under `WinTeam.Mobile.Core/` — ViewModels, Managers, Proxies, Entities, Services, Utilities | 200 | 250 |
| Anything under `WinTeam.Mobile.iOS/` | 350 | 350 |
| Anything under `WinTeam.Mobile.Android/` | 450 | 450 |

The Core cap carries ~50 lines of tolerance, so treat 200 as the target and 250 as the line you do not cross.
Android gets more room than iOS because fragments declare and initialise their views in code.

The "Flag at" column is the machine-readable source of truth, and it lives in one place:
[`thresholds.json`](../../thresholds.json) at the root of this plugin. The edit hook reads it,
`/winteam-standards:size-report`
applies it, and the numbers above restate it for readability. **If this table and that file disagree, the
file is right** — and fix the table.

The platform caps apply to the **whole project**, not only the `Views/` folders. That is deliberate: the
largest files in the iOS project include an app delegate, a coordinator, and a device service, none of which
are views, and none of which have a claim to more room than a view controller does. Folder is also an
unreliable signal here — one of the longest files sits under `Services/` but is a view controller.

Generated files are exempt: `*.Designer.cs`, `*.designer.cs`, and anything with a
`<auto-generated>` header. Never split or hand-edit those.

## When to use

Before adding to a file, not after. Check the line count when you are about to:

- create a new `.cs` file,
- add a method, property, or `#region` to a file already past its target,
- add a second responsibility to a class — a second data source, a second flow, a second timer.

## When NOT to use

- Generated files, and `Constants.cs`-style pure constant lists, where the length is the content.
- A file that is long only because it holds many one-line members (a static string block, a DTO with 40
  properties). Splitting that buys nothing — the metric to watch there is the class's number of
  *responsibilities*, not its lines.
- Deciding whether a *method* is too long or takes too many parameters — that is
  `keeping-core-methods-small`.
- Test files.

## Where the seam goes

Pick the cheapest option that removes a whole responsibility, in this order:

1. **A `partial` class in a second file.** Free, no new type, no wiring, no behaviour change. Right when one
   cohesive block is mechanically separable — message handler registration, a set of computed properties, a
   block of static strings. Name it `Thing.Aspect.cs`.

   ```csharp
   // Thing.cs           — construction, state, the primary flow
   // Thing.Messages.cs  — every Register/Unregister and handler
   public partial class Thing { }
   ```

2. **Extract a collaborator with no base class.** A plain class that manipulates state handed to it. The
   cheapest real extraction, and the first thing to reach for.

   ```csharp
   // Shared state travels in an object; the helper gets capabilities as delegates,
   // so it never holds a reference back to its owner.
   internal sealed class StepInputHelper(FlowState state, Func<Task<bool>> confirmAsync)
   {
       public Task<bool> RunAsync() => confirmAsync();
   }
   ```

3. **Extract a child view model.** Only when the extracted piece owns observable state or handles messages.
   Costs base-class choice, construction-site choice, activation, and teardown — real wiring, so do not
   reach for it first.

   This skill does not own that wiring. If `timeclock-refactor` is installed, use
   `timeclock-refactor:extract-child-view-model` for it — base class, construction site, `[Inject]`,
   activation and teardown, in order. That plugin is opt-in and its paths are branch-specific, so if it does
   not resolve, get the wiring from `wiring-dependency-injection` and `tearing-down-subscriptions` instead and
   say which pieces you could not confirm.

4. **Collapse a wide parameter surface into a record** before extracting anything, if the reason the file is
   long is that several members each thread the same five values through.

   ```csharp
   public readonly record struct RequestContext(
       string Reference, DateTime OccurredAt, bool IsRetry);
   ```

**Name the responsibility out loud before you cut.** Write one sentence: "this new file is the single source
of truth for X." If you cannot finish the sentence, the seam is in the wrong place and you will end up with
two files mutating the same field — strictly worse than one long file.

## Rules

1. **Splitting must not change behaviour.** No reordering of construction, no "while I'm here" fixes. If a
   behaviour change is needed, land it as its own separate change afterwards.
2. **A `partial` split does not reduce the class's responsibility count** — it only makes the file readable.
   Don't treat it as having solved a design problem.
3. **If a class needs an extracted view model, that extraction has its own wiring rules.** Activation and
   teardown are where these go wrong silently. Check `tearing-down-subscriptions` before you finish.
4. **Don't split a file to get under the cap while leaving the responsibilities entangled.** Two files that
   each reach into the other's state are worse than one file. Prefer leaving it long and flagging it.

## Known offenders

Largest hand-written files, worst first, worth knowing so you don't add to them: `DropDown`,
`LoginViewModel`, `TimeClockViewModel`, `MainActivity`, `WTPunchFlowPersistentClient`, `KioskModeManager`,
`PunchesManager`, `Device`, `AppDelegate`. **All are well past their project's cap** — treat any of them as a
file to take something out of, never to add to.

Deliberately no line counts here. A count written into a skill goes stale silently, and these move with every
change to the files named above. The names are what this list is for.

For the live figures — how many files sit over each cap, and by how much — ask the user to run
`/winteam-standards:size-report`, which derives them at run time. A skill cannot invoke a slash command.

## Verify

- The new file's line count and the original's are both under their caps — and if the original is not, say
  so rather than claiming success.
- No behaviour changed: construction order, activation, and teardown are identical.
- `dotnet build WinTeam.Mobile.Core/WinTeam.Mobile.Core.csproj`, plus the iOS/Android csproj if a view binds
  to anything you moved.
