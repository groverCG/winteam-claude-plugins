# AppStrings — centralizing user-facing strings

This repo keeps all user-facing text in one shared, localizable resource: `WinTeam.Mobile.Core/Resources/AppStrings.resx` (English/neutral), with satellite translations in `AppStrings.es.resx` and `AppStrings.fr.resx`. Generated C# accessors live in `AppStrings.Designer.cs` (namespace `WinTeam.Mobile.Core.Resources`), used identically from iOS and Android code as `AppStrings.SomeKey`.

**Important — the Designer.cs file is not auto-regenerated by `dotnet build`.** The `.resx` is configured with `<Generator>PublicResXFileCodeGenerator</Generator>`, which is a Visual Studio single-file-generator (design-time custom tool). On the CLI / non-Windows, saving the `.resx` alone does **not** regenerate `AppStrings.Designer.cs` — the two files will silently drift out of sync unless both are edited together by hand. Every time you add a key to the `.resx`, you must also hand-add the matching property to the `.Designer.cs` in the exact generated style (see below), or the new `AppStrings.*` member won't exist and code referencing it won't compile.

## When to use

Check before writing the string, not after. Any code change that would otherwise contain
`"Some Sentence Or Label"` assigned to a `.Text`, `.Title`, `Message`, the label/body of an alert or toast,
a cell/chip/row title, an `NSAttributedString`/`UIStringAttributes` literal, or a similar UI-facing
property, in a `.cs` file under `WinTeam.Mobile.iOS/`, `WinTeam.Mobile.Android/`, or `WinTeam.Mobile.Core/`.

## When NOT to use

Do not use for non-UI strings: log/`Debug.WriteLine` messages, exception messages, analytics/event names,
resource/asset/drawable names, dictionary/route keys, format specifiers, URLs. Also skip strings that
already reference `AppStrings.*`, and literals in test projects.

## Steps

1. **Search first.** Before adding anything, grep `WinTeam.Mobile.Core/Resources/AppStrings.resx` for the literal text or a close variant — this repo already has 654 keys and duplicates are easy to introduce. Reuse an existing key if one already carries the same text/meaning.

2. **Pick a key name.** PascalCase, descriptive, no spaces. If the string belongs to a specific screen/feature that already has a naming pattern (e.g. `PaycheckSummary`, `PaycheckDetails`, `PaycheckListNoInternetError` for the Paycheck screens), prefix new keys the same way (e.g. `PaycheckFilterEmpty`) so related strings sort together.

3. **Add the entry to `AppStrings.resx`** (append near the end, right before `</root>` — this file is not strictly alphabetized; new features' strings are appended together):
   ```xml
   <data name="YourKeyName" xml:space="preserve">
       <value>Your user-facing text</value>
   </data>
   ```

4. **Add the matching property to `AppStrings.Designer.cs`**, appended at the end of the `AppStrings` class body, matching the existing generated pattern exactly:
   ```csharp
   public static string YourKeyName {
       get {
           return ResourceManager.GetString("YourKeyName", resourceCulture);
       }
   }
   ```

5. **Don't add `.es.resx` / `.fr.resx` entries unless you have real translations.** `ResourceManager` falls back to the neutral `AppStrings.resx` value for any culture missing a key — this repo already has two base-only keys (`CapturePunchPhotoIsDisabledForThisJob` and `PunchSendFailed`, 654 in the base against 652 in each satellite) that rely on this fallback. Never invent a translation; leave the satellite resx files alone (or flag to the user that translations are needed) and let English show through until a real translation is provided.

6. **Replace the literal in the calling code** with `AppStrings.YourKeyName` (add `using WinTeam.Mobile.Core.Resources;` if not already imported).

## Verify

```bash
dotnet build WinTeam.Mobile.iOS/WinTeam.Mobile.iOS.csproj
dotnet build WinTeam.Mobile.Android/WinTeam.Mobile.Android.csproj
```

**What the build proves:** that the `AppStrings.YourKeyName` member exists — i.e. that you did hand-add the
property to `Designer.cs`. A missing property is the only failure mode here that surfaces as a compile error.

**What it cannot catch:**

- **A typo in the `GetString` key.** It compiles and resolves to `null` at runtime, rendering an empty label.
  Check the key string inside `Designer.cs` against the `name` attribute in the `.resx` character for character.
- **A stale `Designer.cs`.** `PublicResXFileCodeGenerator` is a Visual Studio design-time generator, so
  `dotnet build` never regenerates it — the `.resx` and `.Designer.cs` drift silently apart.
- **Wrong copy, or a missing translation.** A key falling back to neutral English in a Spanish session is
  indistinguishable at build time from a correctly translated one. Run the screen in each supported locale.
